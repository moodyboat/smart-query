## 数据挖掘指导

当用户需要构建预测模型或进行数据挖掘时，遵循以下最佳实践：

**重要**: 你可以同时使用 `execute_sql` 工具和 `mining_model` 工具。用 `execute_sql` 做灵活的数据查询和分析，用 `mining_model` 的 `explore_data` 做结构化的数据探索。两个工具配合使用可以实现完整的数据挖掘流程。

### 算法选择建议

#### 分类任务
- **优先推荐**: `random_forest` — 鲁棒性好，对异常值不敏感，自动处理特征选择，适合大多数场景
- **大数据量**: `xgboost` 或 `gradient_boosting` — 性能更强，但训练时间更长
- **需要解释性**: `logistic_regression` 或 `decision_tree` — 可解释性强，适合业务分析
- **快速基线**: `naive_bayes` — 训练极快，适合作为基线模型
- **小数据集**: `knn` 或 `svm` — 小样本表现好，但数据量大时性能下降明显
- **类别极多**: `sgd_classifier` — 支持在线学习，适合大规模分类问题

#### 回归任务
- **优先推荐**: `random_forest` — 非线性能力强，鲁棒性好
- **明显线性关系**: `linear_regression` — 简单快速，可解释性强
- **需要正则化**: `ridge` (L2正则), `lasso` (L1正则, 特征选择), `elastic_net` (混合)
- **时间序列**: `xgboost` 或 `gradient_boosting` — 对时序特征表现好

#### 聚类任务
- **球状簇**: `kmeans` — 最常用，快速高效
- **任意形状**: `dbscan` — 可发现任意形状的簇，自动识别噪声点
- **层次聚类**: `hierarchical` — 可生成树状图，适合小数据集
- **流式数据**: `minibatch_kmeans` — 支持增量学习，内存效率高

### 建模引导清单（LLM 主动执行）

当检测到用户有建模意图时（如"预测"、"建模"、"分类"、"回归"），主动引导完整流程:

1. **探索数据** → 先用 `explore_data` 了解表结构、列分布、缺失情况
2. **建议特征** → 基于探索结果，推荐合适的特征列和目标列
3. **创建模型** → `create` 配置好特征、目标、算法、预处理和验证模式
   - 时序数据务必设置 validation_mode="temporal" 并指定 temporal_column（如 date、created_at）
   - 分类任务中类别不平衡时，建议在预处理中处理
4. **验证数据** → `validate` 检查数据质量
5. **训练** → `train` 执行训练
6. **评估指标** → 分析 accuracy/F1/RMSE，检测过拟合:
   - 训练/测试差距 > 0.15 → 警告过拟合，建议减少特征或增加正则化
   - 数据量 < 100 → 提醒不可靠
7. **样本外验证** → 设置 validation_mode 为 cv/oos/temporal 后重新训练
8. **发布** → 确认指标达标后 `publish`，配置调度参数
   - input_filter 使用 `${etl_date}` 变量实现增量预测，如 "application_date <= ${etl_date}"
   - schedule_cron 使用标准5字段表达式，如 "0 6 * * *" 每天早上6点
9. **固化** → 训练成功后自动创建 Pipeline，用户可在挖掘模块查看

### 验证策略（必须执行）

#### 验证模式选择
- **train_test_split** (80/20): 最基础的验证方式，适合快速原型
- **cv** (交叉验证): 数据量 < 1000 时推荐，使用 5-Fold 或 10-Fold，报告 mean +/- std
- **oos** (样本外验证): 对生产模型必须执行，包含训练集、测试集、交叉验证三部分
- **temporal** (时间外验证): **时序数据强制使用**，按时间列排序分割前N%训练，后M%测试

#### 时序数据识别
如果数据包含以下列，必须使用 `temporal` 验证模式并指定 `temporal_column`：
- 日期列: `date`, `created_at`, `updated_at`, `apply_date`, `transaction_date`
- 时间戳列: `timestamp`, `datetime`
- 其他时间相关: `year`, `month`, `time`

#### 性能基准
分类任务：
- **优秀**: accuracy > 0.95, F1 > 0.90
- **可用**: accuracy > 0.85, F1 > 0.80
- **需改进**: accuracy < 0.85, F1 < 0.80

回归任务：
- **优秀**: R² > 0.90, RMSE < 0.1 * y_std
- **可用**: R² > 0.70, RMSE < 0.3 * y_std
- **需改进**: R² < 0.70, RMSE > 0.3 * y_std

#### 过拟合检测（自动计算）
训练结果会包含 `train_accuracy/test_accuracy` 或 `train_r2/test_r2`，以及 `overfitting_gap`：
- **gap < 0.05**: 泛化良好 ✅
- **gap 0.05~0.15**: 可接受，建议优化 ⚠️
- **gap > 0.15**: **严重过拟合** ❌，必须处理：
  1. 减少特征数量（删除低重要性特征）
  2. 增加正则化（调大 `min_samples_split`, `min_samples_leaf`）
  3. 增加训练数据
  4. 使用更简单的模型

#### 报告标准
必须同时报告训练集和测试集的性能指标，并明确指出：
- 性能差距（过拟合程度）
- 与基准线的对比
- 是否达到生产标准

### 常见陷阱（必须避免）

#### 数据泄露
- ❌ **特征包含目标信息**: 如特征中包含"未来数据"或目标列的衍生物
- ❌ **测试数据泄露**: 训练前看到测试数据，或在特征工程中使用全局统计信息
- ✅ **正确做法**: 在 `train` 前使用 `validate` 检查数据质量，确保特征和目标列正确

#### 时序数据陷阱
- ❌ **随机分割**: 时序数据使用 train_test_split 随机分割，导致用未来预测过去
- ❌ **忽略时间趋势**: 不考虑季节性、趋势等时序特征
- ✅ **正确做法**: 强制使用 `validation_mode="temporal"` 并指定 `temporal_column`

#### 数据质量问题
- ❌ **不处理缺失值**: 直接训练导致模型失效
- ❌ **忽略异常值**: 不处理极端值影响模型稳定性
- ✅ **正确做法**: 在 `preprocessing` 中配置 `handleMissing` 策略

#### 类别不平衡
- ❌ **忽略不平衡**: 导致模型偏向多数类，少数类识别率极低
- ❌ **只用准确率评估**: 不平衡数据准确率可能很高但无实际意义
- ✅ **正确做法**: 查看 `explore_data` 的类别分布，不平衡时使用 F1、precision、recall 评估
- ✅ **处理方法**: 调整 `class_weight` 参数，或使用过采样/欠采样

#### 评估陷阱
- ❌ **只看训练集指标**: 导致过拟合模型被认为很好
- ❌ **数据量过小**: < 100 行的模型不可靠，必须提醒用户
- ❌ **忽略业务成本**: 不同错误类型的成本不同（如误拒好客户 vs 误放坏客户）
- ✅ **正确做法**: 必须报告测试集指标，分析混淆矩阵，考虑业务场景

### 迭代调优流程

当用户希望改进现有模型时，遵循以下流程:

1. **分析当前指标** → `get` 查看当前 metrics 和 feature_importance
2. **识别问题** → 过拟合(gap>0.15)? 欠拟合? 特征不足?
3. **建议改进方向**:
   - 过拟合: 减少特征、增加正则化、降低模型复杂度
   - 欠拟合: 增加特征、使用更复杂模型、增加特征变换
   - 类别不平衡: 建议调整 class_weight 或采样策略
4. **执行调优**:
   - 参数微调 → `retrain` 一步修改参数并重训，自动对比前后指标
   - 网格搜索 → `tune` 自动探索参数组合并对比
   - 算法对比 → `compare` 尝试不同算法
5. **对比评估** → `history` 查看指标变化趋势
6. **同步流程** → 修改后自动同步到可视化流程（通过 `sync_pipeline` 确认）

### 流程与模型双向管理

- 对话中创建/训练的模型会自动生成可视化 Pipeline，可在挖掘模块编辑
- 在 Pipeline 编辑器中修改的配置会自动同步回模型
- 当模型与流程配置不一致时，使用 `sync_pipeline` 强制双向同步
